# Interview notes

Short, honest talking points for discussing this project in a technical interview. Every claim
below can be demonstrated in the code.

## The 60-second pitch

> A simulated vehicle puts DBC-encoded signals on a CAN bus. An edge gateway decodes them, validates
> a once-per-second snapshot, and publishes over MQTT with an on-disk store-and-forward buffer, so
> a dead network never loses data. In AWS an IoT rule triggers a Lambda that validates and stores
> idempotently in DynamoDB, dead-letters malformed messages, and emits metrics. A FastAPI service
> and a small dashboard read the data. Everything is infrastructure as code with CDK, runs locally
> with Docker Compose, and is covered by CI.

## Questions to expect, and where the answer is

| Question | Short answer | Where |
|---|---|---|
| Why 1 Hz to the cloud when CAN runs at 10 Hz? | Cost and bandwidth: ~90 % less traffic; resolution is configurable. Raw high-rate logging would be a separate path (S3/Firehose). | `signal_cache.py`, `GW_PUBLISH_HZ` |
| What if the network drops? | Messages are written to SQLite first and deleted only after PUBACK; order is kept; retries use exponential backoff with jitter. | `buffer.py`, `forwarder.py`, `backoff.py` |
| Exactly-once? | Not with MQTT. QoS 1 is at-least-once; the Lambda writes idempotently (conditional put keyed by vehicle and sampling time). | `repository.py` |
| What about old data arriving after new data? | The latest-state write is conditional on `last_ts < new_ts`; history still stores everything. | `TelemetryRepository.put_latest` |
| Why is the topic ID passed separately? | The topic is authorised by the IoT policy, the payload is not. A mismatch is rejected (spoofing guard). | `validation.py`, IoT rule SQL |
| Malformed message vs. DynamoDB outage? | Malformed is permanent → DLQ, invocation succeeds. Outage is transient → exception → Lambda retry, then DLQ. | `processor.py` |
| How are devices isolated? | One policy with policy variables (`Thing.ThingName`, `Thing.Attributes[vehicle_id]`); a certificate can only connect as its thing and publish under its own topic prefix. | `telemetry_stack.py` |
| Why no certificates in CDK? | A key generated by CloudFormation lives in template state. Keys are created per device with the CLI (or fleet provisioning in production). | README, `_device_registry` |
| Why DBC? | It is the industry-standard description of CAN signals; one file drives encode and decode, and is usable with CANalyzer-class tooling. | `vehicle.dbc`, `can_db.py` |
| How do you get a DTC from a simulation? | The model changes physics (cooling failure); a diagnostic monitor sets the code after a debounce time, like an ECU. | `model.py` (`_update_diagnostics`) |
| How is it tested without AWS? | moto for DynamoDB/SQS, fakes for MQTT, virtual CAN bus, and CDK template assertions. | `tests/` in each package |
| What would you change for 100 000 vehicles? | Fleet list via GSI/pagination, Firehose → S3 for history, provisioning by claim certificate, per-vehicle rate limits, IoT rule batching/Kinesis if Lambda concurrency becomes the bottleneck. | README: improvements |
| What did testing reveal? | An over-broad IAM grant (`DeleteItem`), a DTC raised by a normal cranking voltage dip, and a config crash on empty env vars. | README: lessons learned |

## Honest limits (say them before you are asked)

- Not deployed to a real AWS account from this repository; the template is synthesized and asserted.
- Docker images are built in CI, not on the development machine.
- The API has no authentication yet (planned: Cognito / JWT authorizer).
- The simulator is plausible, not a validated vehicle dynamics model.
